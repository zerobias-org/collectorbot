# Collector Bot Package Structure Rules

This document defines the rules and conventions for collector bot packages in the **zerobias-org/collectorbot** repository. Claude Code MUST follow these rules when developing, modifying, or verifying collector bot code.

## ⚠️ ZeroBias-Org Repository - Package Scopes

**This is the community zerobias-org repository. Content packages come from `@zerobias-org` only; nothing here depends on `@auditlogic` or `@auditmation`.**

| Package Type | Scope in THIS Repo | Notes |
|-------------|-------------------|-------|
| Collectors | `@zerobias-org/collectorbot-*` | |
| Modules | `@zerobias-org/module-*` | No `@auditlogic` fallback |
| Products | `@zerobias-org/product-*` | |
| Schemas | `@zerobias-org/schema-*` (+ `-ts`) | No `@auditlogic` fallback |
| Utilities / types | `@zerobias-org/util-*`, `@zerobias-org/types-core-js` | Replaces `@auditmation/util-*`, `@auditmation/types-*` |
| Platform runtime | `@zerobias-com/*` (`hub-client`, `platform-sdk`, `hub-client-codegen`, `hub-secrets-manager`) | Replaces `@auditmation/hub-*` |

**Legacy bots:** `package/avigilon/alta/access` and `package/auditmation/generic/tls` still reference `@auditlogic/*` schemas/modules. They are pending migration (the `@zerobias-org` schema does not exist yet for Avigilon). Do not copy them as a pattern.

**Package Name Derivation:**
- Directory: `package/<vendor>/<suite?>/<product>/`
- Package: `@zerobias-org/collectorbot-<vendor>-<suite?>-<product>`
- Example: `package/avigilon/alta/access/` → `@zerobias-org/collectorbot-avigilon-alta-access`

**Product Discovery:**
```bash
npm view @zerobias-org/product-bundle --json | jq '.dependencies'
```

## Package Structure Overview

Collector bot packages follow a hierarchical naming convention:

```
package/<vendor>/<suite-if-exists>/<product>/
```

**Rules:**
- `<vendor>` - Always required (e.g., `amazon`, `microsoft`, `google`, `adp`)
- `<suite>` - Optional, only when the vendor has product suites (e.g., `aws` for Amazon, `365` for Microsoft)
- `<product>` - The specific product being collected from (e.g., `iam`, `ec2`, `entra`)

**Examples:**
- `package/amazon/aws/iam/` - AWS IAM collector (vendor=amazon, suite=aws, product=iam)
- `package/amazon/aws/ec2/` - AWS EC2 collector (vendor=amazon, suite=aws, product=ec2)
- `package/microsoft/entra/` - Microsoft Entra collector (vendor=microsoft, no suite, product=entra)
- `package/adp/workforcenowng/` - ADP Workforce Now NG collector (vendor=adp, no suite, product=workforcenowng)
- `package/google/workspace/sheets/` - Google Workspace Sheets (vendor=google, suite=workspace, product=sheets)

**IMPORTANT:** The legacy `collector/` directory at the repository root is **deprecated**. All new collectors MUST be created in the `package/` directory structure.

### Complete File Structure

```
package/<vendor>/<suite-if-exists>/<product>/
├── .gitignore                   # Git ignore rules
├── .mocharc.json               # Mocha test configuration (tsx)
├── .npmrc                      # NPM registry config (regular file, copy of root)
├── .nvmrc                      # Node version (regular file, copy of root)
├── build.gradle.kts            # plugins { id("zb.typescript-collectorbot") }
├── collector.yml               # Collector metadata - schema classes
├── gate-stamp.json             # Written by `zbb gate`; commit it, do NOT gitignore
├── hub.yml                     # Hub module references
├── package.json                # NPM package configuration
├── package-lock.json           # Dependency lock file (npm-shrinkwrap.json is generated by release, not hand-kept)
├── parameters.yml              # Collector input parameters (OpenAPI)
├── tsconfig.json               # TypeScript configuration
├── README.md                   # (optional) Package documentation
├── USERGUIDE.md               # (optional) User guide
├── service-map.yml            # (optional) Service type mappings
├── product-map.yml            # (optional) Product mappings
│
├── generated/                  # Auto-generated code (DO NOT EDIT)
│   ├── BaseClient.ts          # Base client class with injected modules
│   ├── index.ts               # Re-exports all generated modules
│   ├── inversify.config.ts    # Dependency injection container setup
│   ├── types.ts               # Symbol types for DI
│   └── model/
│       ├── index.ts           # Model exports
│       └── Parameters.ts      # (optional) Generated parameters class
│
├── src/                        # Source code (EDITABLE)
│   ├── index.ts               # Module entry point
│   ├── Collector*Impl.ts      # Main collector implementation
│   ├── Mappers.ts             # Data transformation functions
│   ├── Util.ts / utils.ts     # (optional) Utility functions
│   ├── Types.ts / types.ts    # (optional) Custom type definitions
│   ├── Relations.ts           # (optional) Object relationship logic
│   ├── Store.ts               # (optional) State management
│   └── Ensurers.ts            # (optional) Data validation/transformation
│
└── test/
    └── e2e/
        └── Collector*IT.ts    # E2E tests (renamed from test/integration)
```

Linting uses the repo-root flat `eslint.config.js` (extends `@zerobias-org/eslint-config`); packages have no `.eslintrc`.

## Package Naming Conventions

### NPM Package Scopes

**IMPORTANT:** This is the **zerobias-org/collectorbot** repository. Everything content-related is `@zerobias-org`; the platform runtime is `@zerobias-com`.

| Package Type | Scope | Example |
|-------------|-------|---------|
| **Collector bots** (what we develop) | `@zerobias-org/collectorbot-*` | `@zerobias-org/collectorbot-microsoft-azure-azureresourcegraph` |
| **Hub modules** | `@zerobias-org/module-*` | `@zerobias-org/module-microsoft-azure-azureresourcegraph` |
| **Product packages** | `@zerobias-org/product-*` | `@zerobias-org/product-microsoft-azure-azureresourcegraph` |
| **Schema packages** | `@zerobias-org/schema-*` | `@zerobias-org/schema-microsoft-azure` |
| **Schema TypeScript types** | `@zerobias-org/schema-*-ts` | `@zerobias-org/schema-microsoft-azure-ts` |
| **Platform runtime** | `@zerobias-com/hub-client`, `@zerobias-com/platform-sdk` | |
| **Utility packages** | `@zerobias-org/util-collector`, `@zerobias-org/util-codegen` | |
| **Type packages** | `@zerobias-org/types-core-js` | |

**Dependency Priority Rules:**
1. **Modules / products / schemas:** `@zerobias-org/*` only. **Never** fall back to `@auditlogic/*`. If the `@zerobias-org` package does not exist, stop and report it (the module/schema must be published first); do not add an `@auditlogic` dependency.
2. **Products:** `@zerobias-org/product-*` (needed for the product UUID, see below).
3. **Platform runtime:** `@zerobias-com/*` (hub-client, platform-sdk, hub-client-codegen, hub-secrets-manager) is allowed and required.
4. **Utilities / types:** `@zerobias-org/util-*` and `@zerobias-org/types-core-js`. `@auditmation/*` is retired; map any old import with the table in the gradle-migration skill ("Replace old package imports").

### Product Packages (Transitive Dependencies)

**Product packages** provide product metadata and UUIDs:
- **Naming:** `@zerobias-org/product-<vendor>-<suite?>-<product>`
- **Examples:**
  - `@zerobias-org/product-avigilon-alta-access` (vendor=avigilon, suite=alta, product=access)
  - `@zerobias-org/product-github-github` (vendor=github, no suite, product=github)
  - `@zerobias-org/product-amazon-aws-iam` (vendor=amazon, suite=aws, product=iam)
- **Note:** Suite is included with hyphen when present!
- **NOT added to dependencies** - module already depends on it
- **Used for:** Finding product UUID for `hub.yml`

**Discovering Available Products:**

To find all available product packages in the ZeroBias ecosystem:

```bash
npm view @zerobias-org/product-bundle --json | jq '.dependencies'
```

This will list all products following the pattern `@zerobias-org/product-<vendor>-<suite?>-<product>`.

Match the pattern to your collector's directory structure:
- Directory: `package/avigilon/alta/access/` → Product: `@zerobias-org/product-avigilon-alta-access`
- Directory: `package/github/github/` → Product: `@zerobias-org/product-github-github`

### Schema Packages: Base vs TypeScript (-ts)

**CRITICAL:** Understand the difference between base schema packages and their TypeScript counterparts:

| Package | Purpose | Usage |
|---------|---------|-------|
| `@zerobias-org/schema-<name>` | Base schema definition | **Must be in dependencies** - required for runtime system installation even if not imported directly in code |
| `@zerobias-org/schema-<name>-ts` | Generated TypeScript interfaces | **Import in code** - use for type safety when creating batch items and working with schema data types |

**Example in package.json:**
```json
{
  "dependencies": {
    "@zerobias-org/schema-amazon-aws-iam": "^1.16.2",      // Base schema (runtime dependency)
    "@zerobias-org/schema-amazon-aws-iam-ts": "^1.16.2"   // TypeScript types (for imports)
  }
}
```

**Example in Mappers.ts:**
```typescript
// Import TypeScript types from -ts package for type safety
import { AwsIamUser, AwsIamRole } from '@zerobias-org/schema-amazon-aws-iam-ts';

export function toAwsUser(...): AwsIamUser {
  return {
    id: ...,
    name: ...,
  };
}
```

## Root Configuration Files

### `.mocharc.json`

**Purpose:** Mocha test runner configuration

**Rules:**
- File extension must be `ts`
- Requires `tsx` (runs TypeScript natively; `ts-node/register` is retired)
- Timeout set to 6000000ms (100 minutes) for long-running e2e tests

**Template:**
```json
{
  "extension": ["ts"],
  "require": "tsx",
  "timeout": 6000000
}
```

**Validation:**
- [ ] Must be valid JSON
- [ ] Extension must include "ts"
- [ ] `require` is `tsx`
- [ ] Timeout must be exactly 6000000 (100 minutes standard)

---

### `tsconfig.json`

**Purpose:** TypeScript compiler configuration

**Rules:**
- ESM: module and moduleResolution `nodenext`, target/lib `es2024`
- Relative imports need the `.js` extension (e.g. `from './Mappers.js'`); package imports do not
- Output directory: `dist/`
- Includes: `src/**/*`, `test/**/*`, `generated/**/*`
- Excludes: `dist`, `node_modules`
- Decorators must be enabled (for inversify DI)

**Template:**
```json
{
  "compilerOptions": {
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "target": "es2024",
    "lib": ["es2024"],
    "outDir": "dist",
    "strict": true,
    "noImplicitAny": false,
    "useUnknownInCatchVariables": false,
    "declaration": true,
    "sourceMap": true,
    "skipLibCheck": true,
    "types": ["node", "mocha", "chai"],
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true
  },
  "include": ["src/**/*", "generated/**/*", "test/**/*"],
  "exclude": ["dist", "node_modules"]
}
```

**Validation:**
- [ ] `experimentalDecorators` must be `true`
- [ ] `emitDecoratorMetadata` must be `true`
- [ ] `module` / `moduleResolution` are `nodenext`
- [ ] `outDir` must be `dist`
- [ ] Must include `generated/**/*` in includes

### `.gitignore`

**Purpose:** Git ignore patterns

**Template:**
```
node_modules/
dist/
generated/
build/
eslint.config.js
eslint.config.mjs
```

**Rules:**
- `generated/` must be ignored (auto-generated by the Gradle `generate` step)
- `dist/` must be ignored (build output)
- `node_modules/` must be ignored (npm packages)
- **NEVER ignore** `gate-stamp.json` (CI validates it)
- **NEVER include** `.npmrc` or `.nvmrc` in `.gitignore` (they are committed)

---

### `.npmrc` and `.nvmrc`

**Purpose:** NPM and Node.js version configuration

**Rules:**
- **Regular committed files** in each package (git mode 100644), copied from the repo root. Existing collectors in this repo do NOT use symlinks.
- Ensures the registry config and Node version are available when the package is built on its own (the `.npmrc` registry lines cover `@zerobias-org` and `@zerobias-com`)
- Use the root `.nvmrc` Node version (currently `v22.x`); keep the package copy in step with it

**Creating them:**
```bash
cd package/<vendor>/<suite?>/<product>/
cp ../../../../.npmrc .npmrc      # 4 levels deep; use ../../../ for 3 levels
cp ../../../../.nvmrc .nvmrc
```

**Verification:**
```bash
ls -la .npmrc .nvmrc
git ls-files -s .npmrc .nvmrc   # mode 100644 = regular file
```

### ESLint (`eslint.config.js` at repo root)

**Purpose:** ESLint configuration. Collector packages have **no** `.eslintrc`; they are linted by the flat config at the repository root, which extends `@zerobias-org/eslint-config`.

**Rules (enforced by the root config):**
- Parser is `@typescript-eslint/parser`
- Max line length: 150 characters
- `no-await-in-loop` and `no-continue` are off (needed for collectors)
- `no-restricted-syntax` forbids `ForInStatement`, `LabeledStatement`, `WithStatement`
- `generated/`, `dist/` and `node_modules/` are ignored
- Package `devDependencies` include `@zerobias-org/eslint-config`

Run it with `zbb lint` from the package directory.

## Metadata Files

### `collector.yml`

**Purpose:** Defines which schema classes this collector populates

**Structure:**
```yaml
classes:
    # Reference to schema package and its classes
    - "@zerobias-org/schema-<vendor>-<product>":
          - ClassName1
          - ClassName2
    - "@zerobias-org/schema-<vendor>-<product>-<subproduct>":
          - ClassName3
```

**Rules:**
- `classes` is the root key
- Each entry is a schema package name (NPM scope: `@zerobias-org/schema-*`)
- Under each package, list all schema classes this collector creates/updates
- Schema package names must match dependencies in `package.json`
- Comments can be added with `#`

**Example (AWS IAM):**
```yaml
classes:
    - "@zerobias-org/schema-amazon-aws":
          - AwsPolicyStatement
    - "@zerobias-org/schema-amazon-aws-iam":
          - AwsIam
          - AwsIamCustomerPolicy
          - AwsIamGroup
          - AwsIamIdentityProvider
          - AwsIamInlinePolicy
          - AwsIamRole
          - AwsIamUser
```

**Example (Empty/Generic):**
```yaml
classes:
    # The classes should be defined in the input parameters
```

**Validation:**
- [ ] Must have `classes` root key
- [ ] All referenced schema packages must exist in `package.json` dependencies
- [ ] Class names should match actual schema class exports

---

### `hub.yml`

**Purpose:** Defines Hub modules and products this collector uses

**Structure:**
```yaml
modules:
  '@zerobias-org/module-<vendor>-<product>':
    id: <uuid>                    # Module UUID
    name: module-<vendor>-<product>
    module: <ModuleName>          # Module class name

products:
  <vendor>.<product>.<subproduct>:
    id: <uuid>                    # Product UUID
    name: <Human Readable Name>
```

**Rules:**
- `modules` section lists all Hub modules the collector connects to
- `products` section identifies the product being collected from
- Module IDs are UUIDs (get from module package or platform)
- **No `operations` section** - omit it (current collectors do not list operations)
- Shared collectors: the source module is NOT listed under `modules` (see create-collector, "Collector modes")

**Example (Azure Resource Graph):**
```yaml
modules:
  '@zerobias-org/module-microsoft-azure-azureresourcegraph':
    id: 255c7fd5-d08c-427b-aca9-643c673be5d6
    name: module-microsoft-azure-azureresourcegraph
    module: Azureresourcegraph

products:
  microsoft.azure.azureresourcegraph:
    id: 8a6b34b8-036a-549a-b2df-6b4bcc8ccc81
    name: Azure Resource Graph
```

**Example (Empty/Generic):**
```yaml
modules:  {}
products: {}
```

**Validation:**
- [ ] Must have both `modules` and `products` keys (can be empty `{}`)
- [ ] Module package names must match dependencies in `package.json`
- [ ] UUIDs must be valid format

---

### `parameters.yml`

**Purpose:** OpenAPI 3.0 schema defining collector input parameters

**Structure:**
```yaml
openapi: 3.0.3
info:
  description: Stub to use for codegen of parameters for a hub client
  version: ''
  title: '@auditmation/hub-client-codegen'
paths:
  /foo:
    get:
      tags:
        - foo
      operationId: getFoo
      responses:
        '204':
          description: Foo
components:
  schemas:
    Parameters:
      type: object
      # Optional: required fields
      required:
        - fieldName
      properties:
        fieldName:
          type: string
          description: Field description
```

**Rules:**
- Must be valid OpenAPI 3.0.3 specification
- `components.schemas.Parameters` defines the input parameters object
- The `paths` section is a stub for codegen compatibility
- Parameters can have:
  - `type`: string, number, boolean, array, object
  - `description`: Human-readable description
  - `required`: List of required field names
  - `format`: e.g., `uuid` for UUID fields
  - `default`: Default value
  - `example`: Example value
  - `items`: For arrays, defines item schema
  - `$ref`: Reference to other schemas

**Example (Simple - no parameters):**
```yaml
openapi: 3.0.3
info:
  description: Stub to use for codegen of parameters for a hub client
  version: ""
  title: '@auditmation/hub-client-codegen'
paths:
  /foo:
    get:
      tags:
        - foo
      operationId: getFoo
      responses:
        '204':
          description: Foo
components:
  schemas:
    Parameters:
      type: object
```

**Example (With parameters):**
```yaml
openapi: 3.0.3
info:
  description: Stub to use for codegen of parameters for a hub client
  version: ''
  title: '@auditmation/hub-client-codegen'
paths:
  /foo:
    get:
      tags:
        - foo
      operationId: getFoo
      responses:
        '204':
          description: Foo
components:
  schemas:
    Parameters:
      type: object
      required:
        - targetId
      properties:
        targetId:
          description: ID of the target to execute against
          type: string
          format: uuid
        skipServiceTypes:
          type: array
          description: List of service types to skip
          items:
            type: string
          example: ["s3", "ce"]
```

**Validation:**
- [ ] Must be valid OpenAPI 3.0.3
- [ ] Must have `components.schemas.Parameters`
- [ ] `Parameters` must be type `object`

## Package Configuration

### `package.json`

**Purpose:** NPM package configuration

**Naming Convention:**
```
@zerobias-org/collectorbot-<vendor>-<suite?>-<product>
```

**How to Determine Package Name from Directory:**

The package name is derived directly from the directory structure:
- Directory: `package/<vendor>/<suite?>/<product>/`
- Package: `@zerobias-org/collectorbot-<vendor>-<suite?>-<product>`

**Examples:**
- `package/avigilon/alta/access/` → `@zerobias-org/collectorbot-avigilon-alta-access`
- `package/github/github/` → `@zerobias-org/collectorbot-github-github`
- `package/auditmation/generic/tls/` → `@zerobias-org/collectorbot-auditmation-generic-tls`

**Note:** When suite is present, it's included with hyphen: `<vendor>-<suite>-<product>`

**Required Fields:**

| Field | Description | Example |
|-------|-------------|---------|
| `name` | Package name with scope | `@zerobias-org/collectorbot-microsoft-azure-azureresourcegraph` |
| `version` | Semantic version (owned by `zbb version`) | `0.0.0` for a new collector |
| `description` | Short description | `Azure Resource Graph Collector` |
| `license` | License type | `UNLICENSED` |
| `author` | Author email | `team@zerobias.com` |
| `type` | ES module | `module` |
| `main` | Entry point | `dist/src/index.js` |
| `files` | Published files | `["dist", "npm-shrinkwrap.json", "*.yml"]` |
| `overrides` | Pin shared transitive deps | `{"@zerobias-org/types-core-js": "$@zerobias-org/types-core-js", "@zerobias-org/logger": "3.0.9"}` |

There is no `directories` section (remove it from migrated bots).

**Required Scripts:**

The Gradle plugin `zb.typescript-collectorbot` (see `build.gradle.kts`) owns build, generate, validate, test, lint and publish. The only script is:
```json
{
  "scripts": {
    "clean": "rm -rf dist/ generated/"
  }
}
```

Run lifecycle steps with `zbb` from the package directory (`zbb build`, `zbb lint`, `zbb testUnit`, `zbb testDirect`, `zbb gate`) or `./gradlew :<vendor>:<suite?>:<product>:build` from the repo root. The old `generate` / `transpile` / `test:integration` npm scripts are retired.

**Required Dependencies Categories** (exact pins, no `^`, `~` or `latest`; run `npm view <pkg> version`):

1. **Module Dependencies** (`@zerobias-org/module-*`):
   - Hub modules this collector uses
   - Must match entries in `hub.yml`
   - `@zerobias-org` only. If it does not exist, report it; do **not** add `@auditlogic/module-*`
   - Shared collector: the source module is a plain dependency but is NOT in `hub.yml`

2. **Product Dependencies** (`@zerobias-org/product-*`):
   - Product package for the collector's product (source of the product UUID)
   - Must match the product for this collector

3. **Schema Dependencies** (`@zerobias-org/schema-*`):
   - Schema packages for data types
   - Both base schema and TypeScript types (`*-ts`)
   - Must match entries in `collector.yml`
   - `@zerobias-org` only. If it does not exist, report it; do **not** add `@auditlogic/schema-*`

4. **Core Dependencies:**
   - `@zerobias-com/hub-client` - Hub client base
   - `@zerobias-com/platform-sdk` - Platform SDK (replaces the old `@auditmation/module-auditmation-auditmation-platform` / `-hub` modules)
   - `@zerobias-org/util-collector` - Collector utilities (`Batch`; replaces `@auditmation/util-collector-utils`)
   - `@zerobias-org/types-core-js` - Core type definitions
   - `inversify` - Dependency injection
   - `reflect-metadata` - Decorator metadata
   - `@supercharge/promise-pool` - only when the collector uses it (e.g. concurrency in shared mode)

5. **What NOT to Include:**
   - **Vendor packages** - Not used in zerobias-org collectors
   - **Any `@auditlogic/*` or `@auditmation/*` package**
   - `dotenv` (Gradle/zbb manages env); `node-fetch` (Node 22 has built-in `fetch`)

**Peer Dependencies:**
```json
{
  "peerDependencies": {
    "axios": "^1.13.0"
  }
}
```

**Dev Dependencies:**

## Error Handling

### Error Types and When to Use

| Situation | Action | Effect |
|-----------|--------|--------|
| Connection failure, auth error, module unavailable | `throw new Error(...)` | Fails entire collector run |
| API operation fails for all items | `throw new Error(...)` | Fails entire collector run |
| **Pipeline-level problem** (access issue, operation failure) | `throw new Error(...)` | Fails entire collector run |
| **Batch item problem** (mapping issue, missing property, broken link) | `await batch.error(message, data)` | Logs error, continues collection, batch marked red |
| **Data quality issue** (missing optional field, unexpected value) | `await batch.warn(message, data)` | Logs warning, continues collection |

**General Rule:**
- **Error**: Problem with the data/pipeline that affects collection quality
- **Warn**: Data quality issue that doesn't prevent collection

### Error Handling Pattern

```typescript
async run(): Promise<void> {
  // Initialization errors should throw
  try {
    await this.init();
  } catch (error) {
    throw new Error(`Failed to initialize: ${error.message}`);
  }

  // Collection continues on item-level errors
  const batch = await this.initBatchForClass(MyClass);

  await items.forEach(async (item) => {
    try {
      if (!isValid(item)) {
        await batch.warn('Item missing optional data', item);
        return;
      }
      const mapped = toSchemaClass(item);
      await batch.add(mapped, item);
    } catch (err) {
      await batch.error(`Failed to process item: ${err.message}`, item);
    }
  });

  await batch.end();
}
```

## Preview Mode

### Handling Preview Mode

Preview mode limits collection for testing/debugging. **All collectors MUST support preview mode.**

```typescript
@injectable()
export class CollectorImpl extends BaseClient {
  // Calculate preview count: use context value or default to 10
  private previewCount?: number = this.context.previewMode
    ? (this.context.previewCount || 10)
    : undefined;
```

### Preview Count Rules

| Rule | Description |
|------|-------------|
| **Per-batch limit** | Limit each batch to `previewCount` items, not total |
| **Per-source limit** | If collecting from multiple sources (e.g., 2 orgs), limit per source |
| **Use in forEach** | Pass `previewCount` to `PagedResults.forEach()` as the limit parameter |

**Example - Multiple Sources:**
```typescript
// Collecting users from 2 organizations
// With previewCount=10: collect 10 users from EACH org, not 10 total

for (const org of organizations) {
  const usersBatch = await this.initBatchForClass(User);
  const users = await this.module.getUsers(org.id);

  await users.forEach(async (user) => {
    await usersBatch.add(toUser(user), user);
  }, undefined, this.previewCount);  // Limit per org

  await usersBatch.end();
}
```

## Dependency Management

### Version Ranges

| Package Type | Version | Reason |
|--------------|---------|--------|
| Module packages (`@zerobias-org/module-*`) | Exact pin | Reproducible builds |
| Schema packages (`@zerobias-org/schema-*`) | Exact pin | Reproducible builds |
| Core / platform / dev dependencies | Exact pin | Reproducible builds |
| `peerDependencies` (e.g. `axios`) | `^` (caret) from latest | Consumer flexibility |
| TypeScript | Exact (currently `5.9.3`) | Ensure build consistency |

Pin to the exact latest: `npm view <pkg> version`. This is the `gradle-migration` standard; `azureresourcegraph` and the avigilon bot follow it for tooling, while several collectors still carry `^`/`latest` and are reported as WARN (not ERROR) by the validator. Never use `^`, `~` or `latest` for dependencies and devDependencies (the one existing exception is `@zerobias-org/eslint-config`: `latest`).

### Lock file (`package-lock.json`)

**Rules:**
- CI runs `npm ci`, which needs a `package-lock.json` in sync with `package.json`
- `npm-shrinkwrap.json` is generated and packaged by the release flow (it stays in `files`); do not hand-maintain one. If an old one exists, delete it first.
- After any dependency change, regenerate from scratch (never `npm install` over an existing `node_modules`, which prunes platform-specific optional deps CI needs):

```bash
rm -rf node_modules package-lock.json
npm install
npm ci --dry-run      # must pass
```

## Version Management

Versioning and publishing are driven by **`zbb`** (see `zbb.yaml` `lifecycle.version` and `lifecycle.publish`). The CI flow is:

1. `detect` job lists modules with changes under `package/<module>`.
2. `version` job (main only) runs `zbb version --modules=...`, which bumps each changed module's `package.json` and `gate-stamp.json` in a single commit and pushes once. Single-writer by design — keeps the publish matrix from racing on `git push`.
3. `publish` matrix checks out the bumped SHA and runs `zbb publish -PversionAlreadyCommitted=true` per module.

**Implications for contributors:**
- Don't hand-edit `version` in `package.json`; `zbb version` owns it.
- For breaking changes, call out the bump intent in the PR so the reviewer sets the right level when invoking `zbb`.
- Commit messages are free-form — there is no Conventional Commits / commitlint gate.

## Batch Processing and GroupId

### Understanding Batches

Collectors write data to AuditgraphDB using the `Batch<T>` utility from `@zerobias-org/util-collector`. Understanding batch behavior is **CRITICAL** for correct data collection.

### The GroupId Concept

**CRITICAL RULE:** The `groupId` determines how batches interact with existing data.

```typescript
const batch = new Batch<SchemaClass>(
  className,        // Schema class name
  this.platform,    // Platform connector
  this.logger,      // Logger
  jobId,            // Job ID
  tags,             // Optional tags
  groupId           // GROUP ID - CRITICAL
);
```

### GroupId Behavior

When two batches have the **same groupId** for the **same class**:
- If Batch A has 30 items and Batch B has 0 items
- Batch B will **DELETE all 30 items** from Batch A

This is by design to handle object removal from source systems (e.g., deleted users, removed access).

### GroupId Rules

| Scenario | GroupId Strategy | Example |
|----------|-----------------|---------|
| Single data source, global scope | Use account/tenant ID | `${accountId}-global` |
| Single data source, regional scope | Use account + region | `${accountId}-${region}` |
| Multiple independent data sources | Use unique identifier per source | `${accountId}-users-ad`, `${accountId}-users-ldap` |
| Different lists of same class | **MUST use different groupIds** | See example below |

### Example: Correct GroupId Usage

```typescript
// CORRECT: Two different user sources use different groupIds
// AD users and LDAP users are independent lists
const adUsersBatch = new Batch<User>('User', ..., `${accountId}-users-ad`);
const ldapUsersBatch = new Batch<User>('User', ..., `${accountId}-users-ldap`);

// CORRECT: Same source, different regions
const usEastBatch = new Batch<Instance>('Instance', ..., `${accountId}-us-east-1`);
const euWestBatch = new Batch<Instance>('Instance', ..., `${accountId}-eu-west-1`);
```

### Example: INCORRECT GroupId Usage (Data Loss!)

```typescript
// WRONG: Same groupId for different data sources
// The second batch will DELETE items from the first!
const adUsersBatch = new Batch<User>('User', ..., `${accountId}-users`);
const ldapUsersBatch = new Batch<User>('User', ..., `${accountId}-users`);
// ⚠️ LDAP batch will remove all AD users!
```

### Common GroupId Patterns

**AWS Collectors:**
```typescript
// Global resources (IAM, S3, etc.)
groupId = `${accountId}-global-${serviceName}`;

// Regional resources (EC2, RDS, etc.)
groupId = `${accountId}-${region}`;
```

**Multi-tenant Collectors:**
```typescript
// Per-tenant grouping
groupId = `${tenantId}-${resourceType}`;
```

**Best Practice:**
- Always think: "What defines a complete, independent set of this data?"
- When in doubt, use more specific groupIds
- Document your groupId strategy in the collector
